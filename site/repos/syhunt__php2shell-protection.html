初掲載 2026-10-23（はてなブックマーク 2位） GitHub ↗

php2shell（CVE-2026-109618/619）に対するApacheのmultipart POSTブロックルールと機能テストキット

何ができるか

  • Apacheの.htaccessでmultipart/form-data POSTリクエストをブロックするRewriteルールを提供しており、攻撃経路の一つを遮断できる。
  • アップロード不要サイト向け（8MiB制限＋全multipartブロック）とアップロード必要サイト向け（32MiB制限）の2種類の設定例を用意している。
  • テストキットでApacheルールが正しくmultipart POSTを拒否しつつ通常のPOSTを許可しているかを検証できる。
  • PHPのsession.upload_progress.enabledを無効化するINI設定例やmemory_limit緩和策など、CVEごとの推奨PHPコンフィグを文書化している。
  • 最新の研究動向（パッチ後の追加PoC発見や他の研究者報告）を随時README内で更新しており、セキュリティ情報のハブとしても機能している。

なぜ注目されているか

推測 公式パッチ（PHP 8.2.35〜8.5.12）適用前の緊急緩和策として、Apache側でリクエストをブロックするアプローチは多くの組織で即座に実施できる。Syhuntが詳細な背景情報と段階的な設定例を整備したことで、セキュリティ担当者のリファレンスとして広く参照されている。

どんな人に役立つか

パッチ適用が即座にできないサーバー管理者や、多層防御として追加の緩和策を設けたいセキュリティエンジニアに向いている。Apache（mod_php・mod_rewrite）環境が前提で、CGI/FastCGI/PHP-FPM環境では一部設定の扱いが異なる点に注意が必要。

技術的なポイント

  • ApacheのRewriteEngineとLimitRequestBodyディレクティブを組み合わせてリクエストレベルのブロックを実現している。
  • PHPのsession.upload_progress.enabled=0を有効なPHP設定（php.iniまたはFPMプール設定）で無効化することで、CVE-2026-109619のセッション関連攻撃経路を絞り込める。
  • CVE-2026-109618向けには一時的にmemory_limit=-1を設定してOOMによるZendエンジン破壊を回避する方法を解説している（恒久的推奨ではない）。
  • テストキットはApacheルールが期待通りに動作しているかをHTTPレスポンス（403/通過）で確認できる構成になっている。

試し方

  1. リポジトリのhttp/.htaccessまたはhttps/.htaccessをApacheのドキュメントルートに配置する。
  2. Apacheがmod_rewriteを有効にしていること、.htaccess内のRewriteが許可されていることを確認する。
  3. テストキットを使ってmultipart POSTが403で拒否されることと通常のPOSTが通ることを検証する。
  4. PHPのphp.iniでsession.upload_progress.enabled=0を設定し、Webワーカーを再起動する。
